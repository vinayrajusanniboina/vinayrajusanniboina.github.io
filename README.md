## Why Java generates a static site

GitHub Pages serves files. It cannot run a Java process, and no amount of
configuration changes that. So Java runs at **build time**, not at request time:
it reads the content, validates it, renders the HTML, and the resulting folder is
what gets published. The visitor's browser never talks to Java.

That split is what makes the site both free to host and impossible to break by
mistake — a bad content file fails the build, and the live site stays exactly as
it was.

## What is where

```
content/          the site's content. This is what you edit.
  site.yaml         name, email, phone, domain, navigation, home page
  about.yaml        profile, education, skills  (feeds /about/ AND /cv/)
  projects/*.yaml   one file per project
  uploads.yaml      written by `upload` — do not edit by hand

assets/           served as-is: CSS, JS, images, CV PDF
files/            CAD and simulation binaries. NOT in git. Uploaded to R2.
src/main/java/    the generator and the upload CLI
src/main/resources/templates/   the HTML templates
docs/             generated output. NOT in git. Built by CI.
worker/           optional Cloudflare Worker (you probably do not need it)
```

## Requirements

- **JDK 21 or newer.** Check with `java -version`.
- `JAVA_HOME` must be set — the Maven wrapper needs it even though `java` is on
  your PATH.

```powershell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-25"
```

To set it permanently on Windows: Settings → System → About → Advanced system
settings → Environment Variables.

Maven itself is **not** required. `./mvnw` downloads it the first time you run it.

## Build and preview

```bash
./mvnw package -DskipTests
```

On Windows use `.\mvnw.cmd package -DskipTests`. That produces
`target/site-builder.jar`. You only need to repeat it if you change the Java or
the templates — not when you change content.

```bash
java -jar target/site-builder.jar serve
```

Builds the site and serves it at <http://localhost:8080>. Press Ctrl+C to stop.

> Open `docs/index.html` directly and it will look unstyled. That is expected —
> the pages use absolute paths like `/assets/css/site.css`, which need a server.
> Use `serve`.

## Commands

| Command | What it does |
|---|---|
| `java -jar target/site-builder.jar build` | Validate and render into `docs/` |
| `... validate` | Check the content, render nothing |
| `... validate --strict` | Exit non-zero on warnings too |
| `... serve --port 8080` | Build and preview locally |
| `... serve --no-build` | Serve what is already in `docs/` |
| `... new-project my-slug --title "My Project"` | Scaffold a project |
| `... upload` | Push new/changed binaries to Cloudflare R2 |
| `... upload --dry-run` | Show what would be uploaded |
| `... upload --all` | Upload everything under `files/`, not just referenced files |

Running the jar with no arguments does a `build`.

## Publishing

Push to `main`. GitHub Actions validates the content, builds the site and
deploys it — roughly ninety seconds. If validation fails, nothing is deployed
and the live site is untouched.

```bash
git add -A && git commit -m "Add rear upright FEA" && git push
```

## What it produces

Eight pages from two projects today, plus:

- `sitemap.xml`, `robots.txt`, `feed.xml` (RSS)
- `search-index.json` — powers the client-side project search
- JSON-LD `Person` and `CreativeWork` structured data on every page
- Open Graph and Twitter card tags
- `CNAME` and `.nojekyll`, generated from `site.yaml` so the domain lives in one place

## Design notes

**No front-end framework and no front-end build step.** Hand-written semantic
HTML5, one CSS file using custom properties and a `clamp()` type scale, and
vanilla JavaScript. Nothing to keep up to date, nothing that stops working in
three years because a build tool moved on.

**Progressive enhancement throughout.** The project cards are in the HTML, so
filtering and search only add to a page that already works. Maths falls back to
readable monospace TeX if KaTeX cannot load. The 3D viewer falls back to a poster
image. Nothing on the site is a blank space if a script fails.

**Dark and light,** following `prefers-color-scheme` with a manual toggle
persisted in `localStorage`. The theme is applied by a tiny inline script before
first paint, so there is no white flash.

**Accessibility is enforced, not aspirational.** Alt text is a build error, not a
lint warning. Focus states are visible, the lightbox uses a native `<dialog>` so
focus trapping is the browser's job, and `prefers-reduced-motion` is respected.
